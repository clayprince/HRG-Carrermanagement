# Oracle purple-table scripts

Target: Oracle Database 21c, service `XEPDB1`, intended schema `APP_USER`.
These files contain no credentials. No connection or SQL execution was done
while preparing them.

## Scripts

1. `01_purple_tables_preflight.sql` — read-only context and exact quoted-name
   preflight for the 19 purple ERD tables. Stop if service/schema are wrong or
   any target table already exists.
2. `02_create_purple_tables.sql` — legacy inert outline retained for reference.
   Every line is commented; do not execute it.
3. `05_create_purple_tables_final.sql` — active Oracle 21c `CREATE TABLE`
   statements for exactly the 19 purple tables. It is ready for manual review
   and uses explicit technical assumptions that still require team approval.
4. `03_verify_purple_tables.sql` — read-only verification of exact table and
   column names, expected primary keys, the 8 included foreign keys, and the
   current PK/FK/unique/check constraint inventory.

The color-based selection is documented in
[`../drafts/01_erd_purple_audit.md`](../drafts/01_erd_purple_audit.md).
The assumptions, corrections, omitted relationships, and open team decisions
are recorded in
[`../drafts/04_design_decisions.md`](../drafts/04_design_decisions.md).

## Review before execution

The active DDL makes concrete choices for identifier quoting, ID generation,
Oracle type mapping, nullability, and duplicate/special column labels so all
19 tables can be represented in executable DDL. Those choices are assumptions,
not confirmations from the ERD or application. Review the P0/P1/P2 decision
log before executing, especially:

- `GENERATED BY DEFAULT ON NULL AS IDENTITY` for all 19 primary keys;
- chosen `NUMBER`, `VARCHAR2`, `CLOB`, `DATE`, and `TIMESTAMP` mappings and
  string/numeric sizes;
- renamed identifiers and `_2` suffixes used to resolve the four duplicate
  column labels without losing a column occurrence;
- the 8 internal foreign keys included and ambiguous/external relations
  deliberately omitted;
- the absence of `CHECK` constraints for ENUM/status values;
- the treatment of `hr_user.password` as a column expected to hold a hash,
  without implementing authentication behavior.

No blue or pink ERD tables are created. `DAW_USER`, WordPress database objects,
and every object outside the 19 listed names are excluded. The create script
has no `DROP`, `TRUNCATE`, `DELETE`, or seed-data statements. Plain
`CREATE TABLE` statements will error if a table already exists; do not rerun
the file against an existing schema without a separately reviewed migration.

## Manual SQL Developer workflow

1. Open this `oracle/` folder in VS Code. Review the audit and decision log.
2. In Oracle SQL Developer, select the approved connection for service
   `XEPDB1` and schema `APP_USER`; no password is stored in these files.
3. Open and run `01_purple_tables_preflight.sql`. Verify the reported
   `SERVICE_NAME`, `SESSION_USER`, and `CURRENT_SCHEMA`. Review every exact
   quoted-name match. Stop if any target table is present or context is wrong.
4. Review `05_create_purple_tables_final.sql` and obtain team approval for its
   documented assumptions. Run it manually only after approval; it creates
   tables and constraints and is not safe to repeat after successful creation.
5. Run `03_verify_purple_tables.sql` and review missing/different columns,
   PK/FK results, datatype details, and existing constraints.

The preflight and verification files are SELECT-only. They have not been run
against Oracle as part of this work. The active DDL is not claimed as tested
against an Oracle instance.
